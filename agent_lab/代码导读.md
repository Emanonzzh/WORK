## 1. `db.py` —— 数据访问层

**为什么单独一层**：`tools / anomaly / inject_anomalies / report / api / streamlit_app` 六个模块都要连库，参数散落就会"改一次密码改五处"。

```python
def query(sql: str, args: tuple = ()) -> list[dict]:
    """执行**只读**查询，返回 dict 列表（DictCursor）。"""
    conn = connect()
    try:
        with conn.cursor() as cur:
            cur.execute(sql, args)      # 参数走占位符 %s，不做字符串拼接
            return cur.fetchall()
    finally:
        conn.close()                    # finally 保证异常时也关连接
```

要点：
- **占位符 `%s`** 而不是 f-string 拼 SQL —— 防注入第一层；
- 写操作单独放在 `execute()`，并在 docstring 里写明"只给注入脚本用" —— 让"谁能写库"一眼可查。

## 2. `tools.py` —— 工具层（Agent 的"手"）

### 2.1 口径表：为什么把口径**写死在代码里**

```python
METRICS: dict[str, dict[str, str]] = {
    "revenue": {
        "sql": "SUM(payment_amount)",
        "label": "实付额",
        "definition": "销售额默认口径 = SUM(payment_amount)，用户实际支付金额（已扣优惠）",
        "unit": "元",
    },
    "refund_rate": { ..., "definition": "退款订单金额 / 实付额，取值 0~1（不是百分数！）" },
    ...
}
```

> **面试点**：口径不写死，就会出现"同一个问题两次问出两个数"。
> 而且口径**随返回值一起给模型**（见 `query_metrics` 的返回），模型不用猜字段含义。

### 2.2 参数校验：白名单 + **语义范围**

```python
def _check_metric(metric: str) -> None:
    """指标名必须在口径表白名单里（不在就报错，而不是猜一个默认值）。"""
    if metric not in METRICS:
        raise ToolError(f"未知指标 '{metric}'，可用指标：{list(METRICS)}")
```

`_check_date` 里还有一段是**踩坑后加的**：

```python
    if not 1 <= month <= 12:
        raise ToolError(f"{field} 的月份必须在 01~12 之间，收到 '{value}'（不存在 13 月这种月份）")
```

> **面试点**：最初只校验格式（正则），`2025-13-01` 被放行、MySQL 返回空值，
> **模型只能自己去猜"13 月不存在"** —— 本该由工具直接报错。
> 结论：**错误信息越明确，模型自我修正越可靠**。

### 2.3 核心算法：量价三因子分解

```python
    def decompose(rev0, n0, rev1, n1):
        """量价三因子分解：返回 (量效应, 价效应, 交互项)，三项之和恒等于 ΔR。"""
        aov0 = rev0 / n0 if n0 else 0.0
        aov1 = rev1 / n1 if n1 else 0.0
        volume = (n1 - n0) * aov0            # 量效应
        price  = n0 * (aov1 - aov0)          # 价效应
        inter  = (n1 - n0) * (aov1 - aov0)   # 交互项
        return volume, price, inter
```

返回时**每行都带校验值**：

```python
"decompose_sum_check": round(vol + pri + inter - delta, 8),   # 应恒为 0
```

> **面试点**：两因子分解是近似、无法验证；三因子才能**精确加总回总变化**，
> 于是可以写成断言（实测 `0.0`）。这是"结论可验证"的基础。

真实跑出来的结果：10→11 月量效应 **+202.07 万**、价效应 **−51.26 万** → "以量补价"。

### 2.4 `attribution.py` —— 这个算法被谁复用（多层下钻）

`contribution_breakdown` 一次只回答"**哪一层**在动"。业务真正追问的是"那一层里**具体是谁**"：
11 月涨了 138 万 → 微信公众号贡献 77.7 万 → 是这个平台里哪个商品把量拉起来的。
手工做就是每换一个问题重写一遍 SQL，所以固化成一个函数。

**最关键的设计约束：本模块一行 SQL 都不写**，全部经 `tools.call_tool` 走既有工具。

```python
result = call_tool("contribution_breakdown", args)   # 唯一取数入口
```

> **面试点**：这样写不是为了好看。走 `call_tool` 就自动继承了四层保障——
> **只读**、**参数白名单**、**口径随值返回**、**加总闭合断言**。
> 一旦这里出现第二条 SQL 路径，上面四层就都不覆盖了。
> 所以有一条测试专门钉它：`attribution.py` 源码里出现 `SELECT ` / `pymysql` / `db.connect` 就红。

**链条闭合判据**（这是"下钻可信"的全部含义）：

```
chain[i].subset_total_delta  ==  chain[i-1].top[0].delta
```

真库实跑（2025-10 → 2025-11）：

```
[0] platform  全市场 6 组   Δ=1,389,478.21  量 +2,020,698.05 价 −512,555.14 交互 −118,664.70
      top → 微信公众号 Δ=776,684.70（占本层 55.9%）
[1] product   微信公众号内 992 组  Δ=776,684.70        ← 与上一层那一行逐分不差
      top → PR000492 Δ=−64,552.87（订单 10 → 0，即一个停售的商品）
```

**`top_n` 有两个作用，容易被问混，主动说清**：① 每层展示几条；② **只有第 1 条会继续往下钻**。
所以 `top_n=5` 是"每层看 5 条、但只钻最粗的那根枝"，不是"5 条都钻"。

**为什么第二层要过滤**：`contribution_breakdown` 原本没有"只看某个维度值内部"的入参，
第二层根本下不去——所以先给它加 `filter_dimension` / `filter_value`（成对、过白名单、
不得等于本层维度），下钻只是它的调用方。顺序不能反：**先有原语，再有编排**。

## 3. `anomaly.py` —— 异常检测（最难的一块）

### 3.1 四条原则（都在代码注释里）

1. **最小支持度门槛**：订单数 < `min_orders` 的切片不判定（wap网站只有 3 单，任何波动都是"100% 异常"）
2. **周内效应校正**：日粒度脉冲检测的基线取**同一星期几**的滚动中位数
3. **日历校正**：月度值按当月天数归一（2 月 28 天）
4. **稳健统计**：`robust_z = residual / (1.4826 × MAD)`

### 3.2 关键代码：同星期几基线

```python
def _same_weekday_baseline(periods: list[str], values: list[float], weeks: int = 3) -> list[float]:
    """【原则 2】同一星期几的滚动中位数 —— 消掉周内效应。

    周六的基线只看它前后几周的周六，而不是把工作日也算进去。
    """
    wd = [date(*map(int, p.split("-"))).weekday() for p in periods]
    out = []
    for i in range(len(values)):
        cand = [values[j] for j in range(len(values))
                if j != i and wd[j] == wd[i] and abs(j - i) <= weeks * 7]
        out.append(median(cand) if cand else values[i])
    return out
```

### 3.3 水平漂移：**整周对整周**

```python
    w = 7 if freq == "day" else 3
    prev_win, next_win = values[i - w:i], values[i:i + w]
    change_pct = (mean(next_win) - mean(prev_win)) / prev_mean * 100
```

> **面试点（真实教训）**：第一版用「3 天窗口比中位数 + 30% 阈值」跑真实日数据，
> 检出 **175 个"异常"，全是误报** —— 根因是**周内效应**：日销售额周六比周一高 40% 是常态，
> 拿 3 天窗口比等于拿周六比周一。
> 改成整周对整周（175→28）+ 同星期几基线（28→22）。
> **主要功劳是前者**，这点我在日志里也如实写了。

## 4. `inject_anomalies.py` + `evaluate_anomaly.py` —— 评测

### 4.1 为什么要注入

真实数据只有"真实波动"，**没有唯一正确答案**（元旦暴涨算不算该被检出？）。
注入已知异常（fault injection）才能算出精确的 P/R/F1。

```python
    print(f"① 复制 orders → {INJECTED_TABLE} ...")
    execute(f"DROP TABLE IF EXISTS {INJECTED_TABLE}")
    execute(f"CREATE TABLE {INJECTED_TABLE} LIKE orders")
    execute(f"INSERT INTO {INJECTED_TABLE} SELECT * FROM orders")
```

> **关键设计**：**不改原表**。`orders` 保留为干净基线 —— 这是下面"差分口径"的前提。

### 4.2 差分口径

```python
def run_once(min_orders: int) -> dict:
    """干净表与注入表各跑一次检测，并算出"差分池"（注入表新出现、干净表没有的异常）。"""
    clean = detect(DIMENSION, table=CLEAN_TABLE, ...)
    injected = detect(DIMENSION, table=INJECTED_TABLE, ...)
    clean_keys = {key_of(a) for a in clean}
    pool = [a for a in injected if key_of(a) not in clean_keys]
```

> **面试点**：干净表上检出 22 个**真实业务事件**（元旦三平台同时暴涨 +143%/+187%/+192%）。
> 直接比对会把它们全算成误报 → 用差分剔除这个"噪声地板"。

### 4.3 事件化后处理（指标从 35% → 55% 的原因）

```python
def merge_events(detections: list[Anomaly], gap_days: int = EVENT_GAP_DAYS) -> list[dict]:
    """【事件化后处理】把同维度值、间隔 ≤ gap_days 的检出合并成一个事件。"""
```

> **面试点（最值钱的一段）**：严格一对一匹配时 P 只有 35%，我**没有去调阈值**，
> 而是逐条归因那 11 个"误报" —— 发现**全部落在注入事件区间内或前后几天**，
> 它们是持续型异常的「进入点/内部点/恢复点」。
> **这是评测方法的错，不是检测器的错。** 加事件化后处理 → P=54.55%、R=100%、F1=70.59%，
> 且"与所有注入都无关的误报 = 0"。

### 4.4 最终指标

| 口径 | P | R | F1 |
|---|---|---|---|
| 事件化后处理（主） | 54.55% | 100% | 70.59% |
| 严格一对一（对照） | 35.29% | 100% | 52.17% |
| 原始口径（含真实事件） | 15.79% | 100% | 27.27% |


> **面试点 · 全局变量不是"配置"，是跨请求共享的可变状态。**
>
> 最初的写法是让调用方（`/analyze`）临时改写模块全局 `MAX_STEPS`，用完在 `finally` 里还原：
> `old = react.MAX_STEPS` → 赋值 → 调 `run_agent()` → `react.MAX_STEPS = old`。
> 单请求完全正确，但 FastAPI 的同步 `def` 接口跑在**线程池**里，两个并发请求会交错：
>
> ```
> 请求 A: old=8 → 全局设为 3 ────────────────► 还原 8
> 请求 B:            old=3 → 全局设为 10 ──────────► 还原 3（把 A 的设置覆盖/污染）
> ```
>
> 结果是 A 请求可能真的跑满 8~10 步（**多花钱**），还原顺序一乱还会给后续请求留下一个谁也没设过的值。
> 修法：上限作为**参数**沿调用链传下去，循环只读局部变量，模块常量退化为默认值。
> 回归测试见 `tests/test_react_loop.py::test_concurrent_runs_keep_their_own_step_limit`
> 与 `test_analyze_endpoint_passes_limit_as_argument`（钉住 api 与循环之间的契约）。

### 6.5 `eval_set.py` / `p0_single_call.py` / `eval_run.py` —— 三臂对照（"循环到底值不值"）

**臂与臂之间只差两件事**：能不能多次取数、工具报错能不能重试。模型、温度、协议、工具目录全一样。

| 臂 | 工具次数 | 报错可重试 | 24 题结果 |
|---|---|---|---|
| `no_tool` | 0 | — | **0/24**（全部如实拒答，0 题编数） |
| `one_tool` | ≤1 | 否 | **11/24**（多步 0/9） |
| `loop` | ≤8 | 是 | **20/24**（多步 7/9） |

**四个"不让数字骗人"的装置**，被追问时才拿得出来：
1. `--facts-only`：标准答案**现调工具算**，题文件里没有一个业务数字，数据换了题跟着变；
2. `--probe-multi`：拿 411 个"一次调用"候选逐题撞，撞得上的 `multi` 就是标签虚高（我手判被打穿两次之后加的）；
3. `must_name`：链式题必须**连实体名一起对** —— 未过滤的分解会把每个商品的数都列出来，只比数字就能被枚举蒙对；
4. `--rescore`：判分口径改了就用旧结果离线重打（本轮实测与在线一致），不为一个判分 bug 再花一次全量的钱。

细节、失败明细、以及"温度 0 也不等于可复现"（同配置两份全量只对得上 13/75）都在
**`agent_lab/eval/three_arm_eval.md`**。

## 8. 面试"讲代码"路线

**3 分钟版**：`tools.py` 的量价分解（30s）→ `anomaly.py` 的周内效应校正与 175→22（45s）

**10 分钟版**：按本文第 1~6 节顺序，每节讲"做了什么 + 为什么这么设计 + 踩了什么坑"。

## 9. 常见追问（先自己答一遍）

1. 为什么量价分解要用三因子而不是两因子？
2. 为什么基线用**中位数**而不是均值？
3. 为什么 MAD 要乘 1.4826？
4. 为什么用**差分**口径评测，而不是直接比对？
5. 事件化后处理的 gap 取 7 天，取 3 天或 14 天会怎样？
6. 报告数字对账为什么还要做"对账器自测"？
7. `min_orders` 从 10 提到 80，指标怎么变？为什么？
8. ReAct 循环的停止条件有哪几个？少了哪个会出事？
9. 为什么"工具报错后的原样重试"要放行，而"重复调用"要拦？
10. `attribution.py` 为什么一行 SQL 都不写？走 `call_tool` 到底换来了哪四层保障？
11. 下钻链的闭合判据是什么？如果 `chain[1].subset_total_delta` 不等于 `chain[0].top[0].delta`，你按什么顺序去查？（提示：先查 filter 有没有传、再查两层用的是不是同一个月、最后查是不是有维度值为 NULL 被 `COALESCE` 成了"未知"）
12. 这套东西上生产还缺什么？（→ 主动说：未做 FDR 多重校正、只评了 platform 维度、无权限与审计）
13. 你的"循环 vs 单轮"对比里，`one_tool` 臂为什么是 **2 次 LLM 调用 + 1 次工具**，而不是 1 次调用？压成 1 次会怎样？（→ 会退化成 `no_tool`，对照组失去意义；本臂与循环的差别**只有**"能否多次取数、报错能否重试"）
14. pilot 里 `one_tool` 和 `loop` 两题全对，`no_tool` 两题全拒答。这**证伪**了"手写循环有价值"吗？没有的话，它证伪了什么？（→ 它证伪的是"multi 标签"：`contribution_breakdown` 一次返回就带了下钻所需全部字段，所以那批题根本不需要多步。**没证伪循环**，但说明题集选错了 —— 诚实的说法是"在能一次取全的题上循环没有优势，优势在错误恢复和嵌套下钻"）
15. 为什么 `correct` 要同时要求"必含数都说到"**和**"没有授权集外的大数"？只留前半个会漏掉什么？（→ 无工具臂蒙对真数字就拿分；判分器自己也得有阳性对照，见 `tests/test_eval_harness.py` 的 `test_wrong_number_with_tools_is_not_correct_and_is_invented`）

16. 你的 multi 题集被 `--probe-multi` 撞穿过两次（第一次 10/10 全中、第二次 4/10）。分别是什么原因？为什么不能靠人再判一遍 `min_calls`？（→ 第一次是 probe 复用判分的字符串写法，`f"{v:.0f}"` 让所有小数都贡献一个 "0"；第二次是题面 required 不全 + `contribution_breakdown` 一次返回所有维度两个月的数，本身就是一张排名表。**结论：标签这种主观判断必须有个不依赖自觉的裁判**）
17. 为什么 `loop` 臂的编造判定会冤枉它？（→ 判分拿"标准答案的取数计划"当授权，而计划每题只留 top1；循环真查到的十二月第二名就被判成编造。现在授权集取**它自己那几步 observation 的原文**（`pool_from_texts`），连被 `OBS_MAX_CHARS` 截断、解析不成 JSON 的那几步都算数）
18. 全量 25 题跑完，`one_tool` 和 `loop` 在 single 桶**同为 10/10**，`loop` 只在 multi 桶赢（7/9 vs 0/9）。这算好消息还是坏消息？（→ 都是：它说明**循环不是普遍更好**，只在“一次取不全 + 可能报错”的场景才有价值；所以对外只报多步桶那一个数，并且要主动说“单步题用循环就是浪费钱”）
