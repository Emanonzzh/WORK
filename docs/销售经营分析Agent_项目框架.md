## 二、两条线（这是本项目最重要的设计）

| | 主线 | 实验线 `agent_lab/` |
|---|---|---|
| **目的** | 求职作品：结论可复现、可对账 | 学 Agent：把每种机制亲手实现一遍 |
| **形态** | 确定性 DAG，LLM 只在 plan / narrate | 手写 ReAct 循环（不依赖框架） |
| **为什么** | 分析类任务 90% 步骤有唯一正确答案，不该交给模型 | 先搞清框架替你做了什么，再决定用不用它 |
| **共用** | 同一套工具（`agent_lab/tools.py`）、同一个数据库、同一套评测集 | 同左 |
| **现状** | ⬜ 未开始 | ✅ 已跑通 |

> **两条线共用地基**，所以实验线的产物天然是主线的一部分，不是玩具。

## 四、一次完整请求的数据流（现在能跑通的部分）

以 **"11 月销售涨了，是不是靠单量堆的？"** 为例：

```
用户问题
   ↓
p1_react.run_agent()                                    ✅ 手写循环
   │
   ├─ Step 1 · LLM 决策（唯一用模型的地方之一）
   │    Thought: 需要做量价结构分解
   │    Action: contribution_breakdown
   │    Action Input: {"dimension":"platform","period_a":"2025-10","period_b":"2025-11"}
   │         ↓
   │    tools.call_tool()
   │      ① 参数白名单校验（维度枚举 / 月份 01~12 / 年份范围）   ✅
   │      ② 只读 SQL（仅 SELECT）→ MySQL 102,287 行              ✅
   │      ③ 代码计算：量效应 / 价效应 / 交互项 + 加总校验          ✅
   │      ④ 返回口径说明（definition/unit）+ reading_guide       ✅
   │         ↓
   │    Observation 回传（超 1800 字符截断）                     ✅
   │
   ├─ Step 2 · LLM 决策
   │    Thought: 数据足够
   │    Final Answer: 引用工具给的数字，不自己算                 ✅
   │
   ↓
结果 + 完整轨迹（每步 thought / action / args / observation / 耗时 / token）  ✅
   ↓
（待补）数字对账脚本 → 报告渲染 → 落库 → API/UI                ⬜
```

**关键分工**：整条链路里 **LLM 只出现在 Step 1 和 Step 2**；取数、校验、计算、加总校验全部是代码。

## 七、关键设计决策（面试被问"为什么"时的答案）

1. **为什么不让 LLM 自己算数？**
   → 代码算的结果可复现、可对账；模型的职责是"理解问题"和"表达结论"。实测：回答里 5/5 数字全部可回库复算，零幻觉。

2. **为什么工具返回值里要带口径说明？**
   → 避免"同一个问题两次问出两个数"。口径随值一起返回，模型直接引用，不用自己推断字段含义。

3. **为什么量价分解必须是三因子而不是两因子？**
   → `ΔR = 量效应 + 价效应 + 交互项`，三项**精确加总回总变化**才能断言校验（实测闭合 0.0）。少一项就变成近似，无法验证。

4. **为什么工具要只读 + 参数白名单？**
   → Agent 安全第一层。参数校验不到位时，模型会替工具"擦屁股"（实测：`2025-13` 被放过时，模型只能自己推断"13 月不存在"）——**错误信息越明确，模型自我修正越可靠**。

5. **为什么手写 ReAct 而不是直接上框架？**
   → 先知道自己实现时踩什么坑（重复动作检测误伤重试、上下文膨胀、畸形输出），才能在框架上做出正确的选型判断。

6. **为什么不硬塞 RAG？**
   → 结构化数据分析的正确工具是 SQL 和代码，不是向量检索。RAG 在本项目只保留一个用途：**口径说明与政策依据的引用**。

7. **为什么砍掉区域/销售员维度？**
   → 数据里根本没有这两个字段（能力盘点实测）。不做假装有数据的分析。
